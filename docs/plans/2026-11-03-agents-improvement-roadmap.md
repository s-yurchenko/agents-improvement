# План развития agents-improvement

Статус: исторический план. Направление было согласовано 4 ноября 2026 года и пересмотрено по итогам нового интервью 21 ноября 2026 года. Актуальный план — [план от 21 ноября](2026-11-21-agents-improvement-roadmap.md).

Ниже сохранён прежний текст для истории. Наборы Go и TypeScript, общие линтеры, CI и порядок этапов из этого документа не являются текущими обязательствами.

## Цель репозитория

Создать публичный репозиторий с личным набором переиспользуемых проверок и скиллов для проектов. Он должен помогать получать предсказуемое поведение агента, меньше повторять требования и исправлять одни и те же ошибки. Развивать набор небольшими законченными шагами в свободное время.

Проверяемые программно требования закрепляются в инструментах и конфигурациях. Скиллы помогают выполнять работу по этим требованиям и упрощают действия, требующие понимания задачи. Для Codex скиллы распространяются через каталог плагинов этого репозитория.

## Согласованные решения

- Репозиторий планируется публичным; набор прежде всего отражает предпочтения владельца для собственных проектов.
- Первые языки — Go и TypeScript.
- За основу берём готовые инструменты. Для требований, которые они не покрывают, поддерживаем добавление своих проверок.
- Набор проверок включает форматирование, статический анализ, проверку типов там, где она применима, и запуск существующих тестов проекта.
- Одни и те же команды должны запускаться человеком, агентом и в CI.
- Скиллы первой версии ориентированы на Codex. Сами проверки доступны независимо от агента.
- Каждый проект явно закрепляет версию подключённого набора. Обновление выполняется отдельным изменением.
- Нужны примеры интеграции с GitHub Actions и GitLab CI.
- На старте готовим базовые наборы Go и TS. Профили для фреймворков и отдельных типов приложений добавляем по потребности.
- Для разработки достаточно маленьких примеров внутри этой репы. Отдельного прикладного проекта сейчас нет.
- Миграцию старого кода отдельным направлением не развиваем. Git-хуки в первую версию не включаем.
- Правила Git и PR должны проверяться независимо от скилла, который помогает подготовить текст.
- План развития содержит широкий список идей. Подробно прорабатываем ближайший небольшой шаг.

## Проверки и скиллы

У проверяемого требования должен быть один источник правил. Локальная команда и CI используют одну версию конфигурации и исполняемой проверки. Скилл обращается к этим правилам и командам; пользователю не требуется запускать скилл для соблюдения требований.

Например, формат сообщения коммита проверяется отдельной командой. Скилл подготовки коммита изучает изменения, предлагает подходящий текст и запускает эту команду. Проверка смысла описания требует понимания изменений, поэтому остаётся частью работы человека и агента.

Скиллы могут помогать и в процессах, для которых нет однозначной машинной проверки: уточнять требования, составлять план или объяснять результаты ревью. Каждый такой сценарий получает собственный критерий полезности.

## Предлагаемая последовательность

### Этап 1 Контракт подключаемого набора

Определить, что получает потребитель набора: конфигурации, команды, описание версии и инструкцию подключения. Сохранить принятую структуру каталога и плагинов из репозитория; размещение кода проверок и общих конфигураций выбрать при подготовке реализации.

- Выбрать минимальный способ поставки и закрепления версии.
- Описать запуск проверок, сообщения о нарушениях и результат завершения команды.
- Описать подключение дополнительной проверки без создания собственного универсального движка линтинга.
- Выбрать первый язык и поддерживаемые окружения для начального примера.

Готово, когда понятен путь от подключения конкретной версии до запуска проверки в примере проекта.

### Этап 2 Первый базовый набор

Собрать полностью работающий набор для одного из языков. Порядок Go и TS выбрать при старте этапа.

- Выбрать готовые инструменты и небольшой полезный набор правил.
- Закрепить версии инструментов и конфигураций.
- Добавить минимальный корректный пример и отдельные примеры с намеренными нарушениями.
- Подготовить локальные команды проверки и исправления там, где исправление поддерживается.
- Описать подключение выбранной версии набора по инструкции.

Готово, когда корректный пример проходит, ожидаемые нарушения обнаруживаются, а команду можно воспроизвести по инструкции.

### Этап 3 Второй базовый набор

Повторить путь для второго языка, сохранив общий подход к версиям, запуску и диагностике. Команды могут учитывать особенности языка и существующие тесты потребителя.

Готово, когда примеры Go и TS независимо проверяются и используют явные версии своих наборов.

### Этап 4 GitHub Actions и GitLab CI

Подготовить отдельную интеграцию для каждого хостинга. Использовать те же команды и версии, что при локальном запуске.

- Добавить минимальные конфигурации CI для примеров Go и TS.
- Подтвердить успешный и неуспешный результат реальными запусками на каждом хостинге.
- Описать необходимые настройки проекта и права для обязательных проверок перед слиянием.

В GitLab требование успешного выполнения проверок CI и ограничения отправки изменений в защищённую ветку настраиваются отдельно. На GitHub обязательные проверки задаются в правилах защиты репозитория. Применение этих настроек требует соответствующих прав. См. [API проектов GitLab](https://docs.gitlab.com/api/projects/#update-a-project), [защищённые ветки GitLab](https://docs.gitlab.com/user/project/repository/branches/protected/) и [обязательные проверки GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging).

Готово, когда есть воспроизводимые примеры интеграции и понятная инструкция включения ограничений слияния. Автоматизацию серверных настроек можно развивать отдельной задачей.

### Этап 5 Проверки Git и PR

Вернуться к сценарию из [первоначального плана каталога плагинов](2026-05-11-agents-improvement-marketplace.md), начиная с независимо исполняемых проверок.

- Выделить машинно проверяемые требования к сообщениям коммитов, заголовкам и описаниям PR.
- Уточнить, какие сообщения проверять: отдельные коммиты, итоговое сообщение при слиянии или оба варианта.
- Выбрать готовые инструменты и добавить недостающие проверки.
- Подключить команды локально и в CI обоих хостингов.

Conventional Commits и русскоязычные сообщения остаются исходными предпочтениями из прежнего плана. Для общего набора отдельно определить, что проверяется автоматически, а что остаётся рекомендацией при подготовке текста.

Готово, когда правила действуют независимо от запуска скилла и есть примеры корректных и некорректных входных данных.

### Этап 6 Каталог плагинов и первые скиллы

Создать каталог и минимальную упаковку плагинов по структуре из `AGENTS.md`. Для каждого скилла выбрать конкретную повторяющуюся задачу и ожидаемый результат.

- Скилл запуска и разбора проверок использует готовые команды и объясняет нарушения.
- Помощник подготовки коммита и PR использует проверки этапа 5 и правила подтверждения действий.
- Сценарии скиллов проверяются на небольших примерах: запуск нужной команды, разбор нарушения, повторная проверка после исправления.
- Манифесты валидируются, пути к скиллам и примеры подключения проверяются.

Готово, когда скиллы можно подключить к Codex и пройти их сценарии на примерах этой репы.

### Этап 7 Упрощение подключения и обновления

После проверки ручного подключения упаковать повторяемые действия в команду настройки.

- Подключать выбранный набор и его явную версию.
- Создавать или дополнять конфиги, команды и конфигурацию выбранного CI.
- Показывать изменения в файлах для просмотра.
- Поддержать явное обновление версии с описанием изменившихся требований.

Готово, когда на чистом примере можно воспроизвести установку, запуск и обновление. Подключение к прикладному проекту станет дополнительной проверкой при появлении такого проекта.

## Кандидаты для дальнейшего развития

Это список возможных задач. Перед реализацией выбираем полезный сценарий, небольшой объём и способ проверки результата.

| Направление | Возможные улучшения | Признак полезности |
| --- | --- | --- |
| Правила Go | Дополнительные проверки ошибок, обработки ресурсов, тестов и соглашений проекта | Каждое правило обнаруживает конкретное нежелательное поведение на примере |
| Правила TS | Дополнительные проверки типов, асинхронного кода, импортов и тестов | Каждое правило имеет понятную диагностику и пример исправления |
| Свои проверки | Расширения готовых инструментов для требований, которые ими не покрываются | Новое правило подключается к обычному запуску и CI |
| Конфигурации и документация | Проверки JSON, YAML, структуры файлов, ссылок и оформления документации | Ошибки обнаруживаются автоматически до принятия изменений |
| Профили приложений | Наборы для конкретного типа Go или TS проекта | Профиль решает потребность появившегося проекта |
| Контекст для агента | Подготовка кратких инструкций о проекте, командах и критериях готовности | Агент находит нужные правила и запускает правильные команды |
| Уточнение задачи | Скилл разбора цели, ограничений и ожидаемого результата | Перед реализацией есть общее понимание задачи |
| Планирование | Скилл разбиения большой задачи на небольшие проверяемые шаги | Каждый шаг даёт законченный результат |
| Работа с нарушениями | Скилл разбора и исправления ошибок проверок | Исправления подтверждаются повторным запуском |
| Ревью | Скилл проверки изменений относительно требований и действующих правил | Замечания конкретны и относятся к изменению |
| Работа с Git и PR | Подготовка описаний и исправление нарушений по результатам проверок | Тексты соответствуют изменениям и правилам |
| Обновление набора | Команды и скилл подготовки обновления с описанием последствий | Проект обновляется на выбранную версию понятным изменением |
| Настройки хостинга | Отдельная автоматизация ограничений слияния через API | Настройки воспроизводимы и применяются при наличии нужных прав |

## Как выбирать следующий шаг

Выбирать одну небольшую задачу, которая либо приносит самостоятельную пользу, либо разблокирует следующий работающий пример. Для неё указывать ожидаемый результат, зависимости и способ проверки. После выполнения обновлять план развития и добавлять идеи, появившиеся из использования.

Подробные правила линтеров, инструменты, способ поставки, поддерживаемые окружения и порядок первого языка определяются в ближайших задачах. Сроки и расписание работы заранее не фиксируются.

Первый рабочий результат — версионированный базовый набор одного языка с локальным запуском на корректном примере и на примерах с нарушениями. Затем добавляются второй язык, оба CI и удобство работы через скиллы.
